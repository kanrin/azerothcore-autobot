# 60 · 工作流与完成定义

## 开始任何任务前

1. 读本目录全部规则（`00`–`60`），尤其与任务相关的那个（协议 → `30`，功能 → `40`，测试 → `50`）。
2. 若是协议/包相关：先打开 AC 源码里的对应 `Packets/*.h` 的 `Read()` 与 `Handlers/*.cpp`。
3. 若是复用上游：先看 `github.com/azerothcore/AzerothGhost` 里有没有现成实现（`references/capability-map.md`），
   有就复用而不是重写；没有才自建。
4. 明确本次任务的**验收证据**是什么（哪条命令、看到什么日志/包/DB 结果）。

## 开发循环

```
设计(对齐规则) → 写编解码/状态机 + golden 单测 → go build/vet/test 全绿
   → 起服务端 → 实盘跑最小用例 → 收集证据（日志/包/DB）
   → 不合格则回退到失败分类(P/R)定位 → 修 → 再来
   → 更新文档/规则（如果发现了新的坑）→ 提交
```

小步快跑：一次只让一个功能状态机前进一格，先证明"发出去 → 收回来"再谈决策。

## 完成定义（DoD）

- [ ] `gofmt -l .` 无输出，`go vet ./...`、`go build ./...`、`go test ./...` 通过。
- [ ] 新增/修改的协议编解码有 golden bytes 单测。
- [ ] 至少一条实盘用例（`-tags=e2e`）验证了该功能，且用的是等待器而非 sleep。
- [ ] 证据可复现：给出运行命令 + 关键日志/DB 查询 + 结论。
- [ ] 没有引入未清理的世界状态（刷怪、账号、角色、队伍、队列）。
- [ ] 日志足以在 1 分钟内定位"卡在哪一步、为什么"。
- [ ] 文档/规则已同步（新坑写进对应规则或 skill 的 references）。

## 必须停下来问用户的时机

1. 需要修改 `/Users/orz/Projects/other/azerothcore-wotlk` 里的任何文件。
2. 需要引入新的第三方依赖，或需要 fork AzerothGhost。
3. 证据指向服务端 bug（给出：复现命令、期望 vs 实际、AC 源码相关行、日志时间对齐）。
4. 任务范围超出 `00-project.md` 的五大能力（例如支持公共服、支持 8.x 协议、压测舰队）。
5. 需要真实玩家账号、需要动非 bot 数据，或需要关闭服务端安全机制（Warden 之外的新机制）。

提问时带上：已试过的方案、观察到的证据、你建议的选项 —— 让用户只需确认或改一个判断。

## 反模式（出现即视为缺陷）

- 凭记忆写包格式；用 `time.Sleep` 代替等待；无限重试；吞掉错误只打日志继续跑。
- 在多个 goroutine 里直接往 socket 写包；把 `WorldClient` 内部状态当本地真相长期缓存。
- 直接改 DB 让功能"看起来成了"（除 provisioning/cleanup）；用 GM 命令当作正常功能路径。
- 实盘测试里共用坐标、裸 `.npc add`、跑完不清理、用 `SoftPass` 掩盖不确定结论。
- 复制粘贴上游代码到本项目却不注明来源，或把上游逻辑改一个名字当成自研。
- 为了通过改动服务端或放宽断言。

## 提交与记录

- commit：`type(scope): 摘要`，body 写验证方式；一个逻辑改动一个提交。
- 遇到新的服务端行为/坑：写进对应规则文件或 skill 的 `references/`，并在 commit 里一并提交。
- 长期设计变更（分层、依赖、里程碑调整）：先改规则再改代码，并让用户确认。
